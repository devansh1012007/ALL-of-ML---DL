## 3. Root cause
`AuthView` never stored `err.status`. Aria attrs keyed only on `error` truthiness, so every failure (username conflict, credential 400, transient 429/network/5xx, invite 403) produced identical both-fields-invalid marking. The `err.status` needed for the fix was already attached by `apiFetch` (`shared.jsx:239`) and already consumed for the alert TEXT (`AuthView.jsx:37-42`) — the state shape simply dropped it. Root-cause fix: persist `errorStatus` alongside `error` and gate each field's attrs on a whitelist helper; no `shared.jsx`/backend change.

## 4. Approach chosen and why
**Approach A (plan-recommended, this run):** two scalars `error` + `errorStatus` (`null`=none initial, `undefined`=network/no-status, else HTTP number) + pure module-scope `ariaFor(status)` first-branch helper. Minimal diff (18 insertions in `AuthView.jsx`), alert JSX untouched, test-through-DOM only (no helper export), no contract change.
- `ariaFor(status)`: `409→{uIn:true,pIn:false,uDe:true,pDe:false}`; `400→{true,true,true,true}`; else→`{false,false,true,true}`. The `else` first-branch structure is the F-01 whitelist: any unknown/future status (404/405/422/401/429/≥500/`undefined`) can only over-announce (describedby) but never falsely claim a field invalid. Only 400 has affirmative invalid evidence (credential fields + register validation both involve the form fields; email [F-09] register-400 conflation — short-password/reserved-name still overlabels subcases — accepted per plan without string parsing).
- `handleSubmit` clears BOTH (`setError(null); setErrorStatus(null)`) so a stale status can never leave a dangling `aria-describedby` (F-02). Catch: `setError(...)` text mapping UNCHANGED; then `setErrorStatus(err.status)` — network `Error` has no `status` property → stores `undefined`; HTTP errors → number. Never string-parse `err.message`. Attrs: `error && xIn ? true : undefined` / `error && xDe ? 'auth-error' : undefined` — never literal `false`, so pre-error DOM unchanged (omission semantics per F-08 + existing guard test).
- DECISION — `err.status` direct vs `'status' in err` guard: used direct `err.status` for consistency with the existing adjacent `err.status === 409/429` reads (apiFetch always throws a real `Error`; `err.status` is safe). Network→`undefined` and HTTP→number both hold. A `'status' in err` guard would be equivalent here and heavier; no `?? null` coercion (would conflate network with none).
- INVARIANT: alert renders iff `error` truthy (`AuthView.jsx:73`); every describedby is gated on `error` truthiness too, so any present `describedby` always resolves to `#auth-error`. For 409, password describedby is absent (not dangling). Invariant is tested (§7).
- **Rejected B (single-object state `{message,status}|null`):** same mapping, larger churn (rewrites alert condition + all `error` reads) for no behavioral gain; two scalars keep existing JSX identical. **Rejected C (parse `err.message` for "already taken" etc.):** brittle, i18n/version-fragile, explicitly forbidden by reviewer + brief.
