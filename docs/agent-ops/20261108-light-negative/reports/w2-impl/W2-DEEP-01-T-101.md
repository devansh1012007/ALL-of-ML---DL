# Design record — W2-DEEP-01 — T-101 light palette + theme contract

Binding for W2-IMPL-01. Deviations require ORCH approval; palette values below are final unless a
reviewer recomputes a different value that meets every threshold in D2 including the wash inventory.

## How the numbers were computed (reviewer-recomputable)

Computation: small Python scripts run from the approved temp dir (`contrast.py`, `contrast2.py`,
`contrast3.py`, `contrast_final.py`, all authoring-only, no repo source touched), using WCAG 2.x
relative luminance: linearize each channel `c' = c/255; lin = c'/12.92 if c'<=0.04045 else
((c'+0.055)/1.055)^2.4`, then `L = 0.2126·linR + 0.7152·linG + 0.0722·linB`, ratio
`(Llight+0.05)/(Ldark+0.05)`. Composites use `comp(fg, alpha, bg) = alpha·fg + (1-alpha)·bg`
per channel, rounded to the nearest integer (browser sRGB alpha compositing over opaque bg).
Every ratio below was produced by those scripts and can be recomputed by hand from the RGB
triples — no eyeballing, no mechanical 255−x inversion.

## D1. Design decision record

**Decision (Option A, restated):** CSS-variable inversion via `[data-theme="light"]` on `<html>`.
`:root` keeps today's dark triples byte-identical (default/no-JS/at-rest = dark). A new
`[data-theme="light"]` block overrides the SAME 14 token names + `color-scheme: light`.
`tailwind.config.js` is NOT touched (token names are the contract — `[VERIFIED frontend/tailwind.config.js:3-24]`).
Theme state lives in `App` (sole common ancestor of `MainApp` header toggle and `AuthView` card
toggle — `[VERIFIED frontend/App.jsx:175-187]`, `[VERIFIED frontend/views/AuthView.jsx:48-89]`);
all writes (attribute + meta + `prime_theme`) go through one `applyTheme()` in new
`frontend/components/theme.jsx` (covered by existing `components/**` content glob
`[VERIFIED frontend/tailwind.config.js:6]` — no config change). A fully `try/catch`-guarded inline
script in `<head>` before the stylesheet/module entries resolves preference once and sets BOTH
`documentElement.dataset.theme` and the meta color-scheme `content` from that single resolution
(pre-paint, no FOUC). Toggle placement: header right cluster next to "Sign out", OUTSIDE `<nav>`
(`[VERIFIED frontend/App.jsx:136]` nav role queried by smoke tests; header cluster at
`App.jsx:148-159`), plus the SAME `ThemeToggle` on the AuthView sign-in card. `NewJob.jsx:678`
`text-orange-400` → `text-warn` (no new token; see D5).

**Toggle exact accessible label (binding, P-10 source of truth):**
dark → `"Switch to light mode"`; light → `"Switch to dark mode"`. Plain `<button aria-pressed>`;
`aria-pressed="true"` iff light is active. Fits header width (two visible words like "Sign out" at
similar length, no truncation), describes the ACTION (not state), and collides with none of the nav
names "Runs"/"Models"/"New run"/"Admin" (`[VERIFIED frontend/App.jsx:124-129]`). `theme.test.jsx`
MUST query `getByRole('button', {name: /switch to (light|dark) mode/i})`.

**Invariants that must hold:**
1. Dark `:root` 14 triples textually unchanged from 85acdda (automated in D6).
2. Attribute/meta/storage always agree after any flip (single `applyTheme` path, no split-brain).
3. `prime_theme` NEVER cleared on sign-out (`logout` removes only `prime_token`
   `[VERIFIED frontend/components/shared.jsx:175-179]` — belt-and-braces pin, don't "fix" it away).
4. Resolution once at load; no `matchMedia`/`storage` listeners (no live sync, last-write-wins).
5. Stored-value write path: only values exactly `"light"`/`"dark"` touch `dataset.theme`;
   anything else falls through to system (D4).
6. Light block defines exactly the same 14 token names (no renames — every utility resolves
   through `token(name)` `[VERIFIED frontend/tailwind.config.js:3]`).
7. No hardcoded hex/palette utilities introduced in shipped JSX (acceptance greps, spec §5.5).

### 2.4 The two honest exceptions / proofs (reviewer must recompute)

**(a) raised-on-canvas 1.18:1 cannot meet 3:1 — accept or redesign.** Raising 226 232 240 to
3:1 vs canvas would require luminance ≤0.29 (a mid-gray surface), on which ink 30 41 59 would
fall below 4.5:1 — the two requirements are mutually exclusive. Resolution: `raised` is a FILL
surface, never a boundary. Every shipped raised consumer is either bordered by `--rule`
(panels/cards) or is a Bar/usage track whose meaningful edge is the accent/ok/warn FILL
(5.44:1 on raised, computed above). The boundary contract is rule/canvas 3.36:1. If the reviewer
rejects this, the alternative is deleting `raised` as a standalone surface (token-only change
impossible) — escalate, do not darken raised past 226 232 240 without recomputing faint/raised.

**(b) accent-ink MUST be white in light (the "stays dark-on-blue" hypothesis fails the math).**
With near-black ink (L≈0.009), accent-ink/accent ≥4.5 forces L_accent ≥0.211, while
accent-as-text on white-canvas requires L_accent ≤0.183 (and ≤0.157 on surface) — an empty
interval. The spec's "(expect it stays dark-on-blue)" is therefore unachievable in light while
accent doubles as ≥4.5:1 link text; W1 §3.5's feasibility claim holds only because it never
checked the dual-role conjunction. White ink resolves it cleanly: 6.70:1 and 8.72:1, with accent
29 78 216 still a solid 5.44:1 fill on raised. Impl MUST ship white accent-ink in the light
block (dark block keeps 10 18 32). This is a NEEDS-ORCH-ACK item — flagged here, not hidden.

## D3. Load and scalability analysis

Pure client theme: one `localStorage` key (`prime_theme`, ≤4 bytes), one `documentElement`
attribute write + one `meta` content write per flip. `applyTheme()` is a pure DOM write
(assign `dataset.theme`, set meta `content`, `localStorage.setItem` in try/catch) — no React
state batching, no network, no timers, no listeners. StrictMode double-render and HMR: attribute
assignment is idempotent; init runs once at load so neither needs handling. O(1) per toggle,
zero render cost (no re-render of views; CSS variables cascade). Concurrency: two tabs
last-write-wins on reload (no `storage` listener, per spec P-09). 100× toggles: still O(1)
writes, no accumulation (no history, no queue). Partial failure: storage throw → in-memory flip
persists until reload (D4). No hot path, no contention, no backpressure.

## D4. Security / hostile guards

Trust boundary: `prime_theme` is attacker/user-controllable via devtools. Mitigations (exact,
binding on impl):
1. Allow-list only: `resolveTheme()` returns `"light"` iff stored value `=== "light"`, `"dark"`
   iff `=== "dark"`, else falls through to `matchMedia("(prefers-color-scheme: light)")`, else
   `"dark"`. The resolved value — never the raw stored string — is assigned to
   `documentElement.dataset.theme` (an allow-listed property assignment).
2. Write paths never reach `innerHTML`/`outerHTML`/`document.write`/selector strings: grep-able
   in impl review (no `innerHTML` in `components/theme.jsx`, `App.jsx`, `AuthView.jsx`,
   init script). Hostile values test set: `"><script>alert(1)</script>`, 10KB string,
   unicode-only, empty string, `"LIGHT"` (case) — all must resolve to default, create no
   element/script, and toggle must still work.
3. Environment guards (P-02, exact): `resolveTheme()` checks
   `typeof window.matchMedia === 'function'` before calling it; the `localStorage` READ is
   wrapped in `try/catch` (access itself can throw, e.g. iframe sandbox/private mode), and the
   WRITE in `applyTheme()` is wrapped separately so a throw still flips attribute+meta
   in-memory without crashing render. Any absence/throw → fall-through to dark, never an
   uncaught exception out of a render path. The head init script mirrors all three guards
   inside one outer `try/catch` with silent fall-through to dark (P-01).
4. jsdom: `matchMedia` undefined → guard path; tests stub it per test (light- and dark-preferring).
   Residual: none (no auth/session data in this key; not cleared on sign-out by design, D1#3).
